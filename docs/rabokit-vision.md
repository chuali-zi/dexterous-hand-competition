# 垒砖 RGB 接入（2026-10-17）

用户本轮同意按有相机的方案推进，随后明确告知相机使用已得到许可确认。以下记录开发副本实测；不扩展为深度、点云或物体真值使用许可。

## 场景与相机

在已有「华北五省大学生机器人大赛 - 垒砖砌筑 副本」的固定底座零件上添加 `base_cam`。没有移动砖块或修改碰撞、质量、摩擦。配置来源见 [rabokit-camera.json](../configs/rabokit-camera.json)，可按其中参数恢复：

- 父零件：`base/r6ef2dc_link_57d50b5359`；相对安装位置 `(0.65, 0, 1.4)` m。
- 原生相机 X/Y 轴：`(1, 0, 0)` / `(0, 1, 0)`；固定俯视。
- 最终图像：320×240，垂直视场角 35°，5 Hz；深度与点云关闭。640×480 曾用于细节检查，因传输问题没有作为最终连续采集配置。
- 相对话题：`base/base_cam/image_raw`、`base/base_cam/camera_info`。

这些是手动安装参数，**不是已经验证的 `T_base_camera` 标定结果**。相机 optical 坐标与原生相机轴约定要区分；机器人 SDK 控制参考系仍需核对。

## 已实现与复现

[采集脚本](../scripts/rabokit_camera.py) 只订阅当前仿真命名空间下明确指定的 RGB 与 CameraInfo，配对时间戳和 frame_id 一致的消息，检查编码、尺寸和针孔内参，保存 `frame.png`、`frame.ppm` 与 `camera.json`。记录使用仿真消息时间戳；等待采用有界的墙钟时间。实际发布端为 RELIABLE，最终脚本使用相同可靠性与深度 5。没有 SDK 或运动调用。

```bash
python competition/scripts/rabokit_camera.py \
  --topic base/base_cam/image_raw --output runs/brick-camera-01

python competition/scripts/rabokit_bricks.py runs/brick-camera-01
```

输出目录必须是新目录。脚本依赖云端已有 ROS；PNG 写入和颜色检测不需要另外安装图像库。

[砖块检测脚本](../scripts/rabokit_bricks.py) 复用已有连通区域提取，先以高饱和主色排除木纹和深色文字，再筛选足够大且近方形的候选。贴边、细长或合并区域单独列为拒绝项。该检测器适用于当前固定俯视场景，输出像素中心和边界，不输出机械臂目标，也不证明抓取成功。

## 实测

相机采集版本 `4aa516b`；640×480 参数和候选检测版本 `3b729e6`。

1. 初始 320×240、70° 视场：6 秒收到 30 张 rgb8 图像和 30 条内参，时间戳配对成功，退出码 0。但砖块只有数个像素，不适合定位。
2. 改为 640×480、35° 后，启动阶段的第一次 6 秒采集收到 1 张图像、7 条内参，配对成功，退出码 0。不能据此宣称这一轮已经达到稳定 5 Hz；需要就绪后的连续复采。
3. 从第二次程序采集的实际 PNG 取回本地，运行 `3b729e6` 检测得到 10 个候选：红 4、黄 3、蓝 2、绿 1；顶面连通区域为 400–420 像素，近似 20×20。未检出桌面文字候选，拒绝区域为 0。这是当前一张实际帧的结果，不是多视角或遮挡条件下的通用检出率。
4. 640×480 在场景就绪后复采：6 秒收到图像 9、内参 22，配对与检测成功，仍得到上述 10 个候选。探针使用 best-effort；不能称为稳定 5 Hz。
5. 将订阅改为 RELIABLE 后，640×480 的 6 秒试验为图像 0、内参 30，采集超时并退出 1。该设置没有解决大帧传输，不记为通过。
6. 保持 RELIABLE，将场景改为 320×240、35°、5 Hz，6 秒收到图像 30、内参 30，配对成功并退出 0。内参 `fx=fy=380.59137628358553`，`cx=160`、`cy=120`，`frame_id=base_cam_optical`，无畸变。
7. 同一最终配置再做一轮 6 秒采集：图像 31、内参 30，配对和检测均成功，退出 0。两轮均为红 4、黄 3、蓝 2、绿 1，总计 10 个候选、0 个拒绝区域；最终各候选顶面均为 100 像素、约 10×10。此处只说明这两段静态场景记录约 5 Hz，不外推长期连续运行或运动遮挡下的表现。

云端 GitHub 拉取后续检测提交时出现 GnuTLS `-110`，一次有界重试 30 秒超时。后续使用本地**已经推送到同一 GitHub 项目**的提交生成 Git bundle，经原云端终端传入临时文件，再 `pull --ff-only` 快进；未更换 origin 或放宽 TLS 检查。检测版本 `3b729e6`、可靠传输版本 `019e1f5` 均以此方式实际更新至云端。

SDK 3.0.0 安装通过；首次只读构造因缺少 `requests` 退出 1。补齐该依赖后，双臂 `get_joint_angles()` 与 `get_pose()` 成功，退出 0；本地 [依赖清单](../rabokit/requirements.txt) 已补入 requests。SDK 本体反馈在当前初始姿态下，左右末端约为 `(0, +0.222, -0.6082)` / `(0, -0.222, -0.6082)` m。没有发送运动命令，也没有将此反馈当作相机外参标定。

本地完成语法、两个脚本的参数入口及 5 项相关单元检查，覆盖 BGR/行填充、深度和畸形数据拒绝、PNG 解码回环、木纹/文字分离、正常方块与合并区域区分。没有为此次独立脚本改动重跑完整离线算法实验。

本地实际图像与检测输出放在已忽略的 `runs/`；云端采集在 `/tmp/brick-camera-01` 至 `/tmp/brick-camera-06`（04 采集失败，没有生成成功输出目录），检测在对应 `/tmp/brick-detections-*.json`。这些临时数据不作为持久开发备份。
